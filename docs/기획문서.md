# 항공자동조회 기획문서

작성일: 2026-06-29

## 목표

항공자동조회는 노선/편명 마스터를 기준으로 TOPAS에서 출발편과 귀국편을 자동 조회하고, 날짜별 운항 여부와 가용 클래스를 정리한 뒤 요금계산과 엑셀 생성까지 이어가는 별도 자동화 프로젝트다.

## MVP 목표

1차 MVP는 ERP 저장을 하지 않는다.

MVP 산출물:

- 노선/편명 마스터 `mjs` 파일
- 조회 시작일/조회 종료일 기준 출발편 TOPAS 원문
- 조회 시작일/조회 종료일 기준 귀국편 TOPAS 원문
- 날짜별 운항 여부 요약
- 날짜별 가용 클래스 요약
- 박수 자동 계산 결과
- 요금계산 결과
- 엑셀 파일

## 기본 실행 흐름

권장 실행 순서:

1. 노선/편명 마스터 `mjs` 파일을 로드한다.
2. `mjs`에서 읽은 노선을 카테고리 체크박스로 보여주고 조회 대상을 고른다.
3. 조회 시작일과 조회 종료일 기준 날짜 목록을 생성한다.
4. 상품일수 기본값을 적용한다. 기본은 5일이다.
5. 출발편 TOPAS 조회 명령을 생성한다.
6. TOPAS에 출발편 명령을 순차 입력하고 AC1 반복 조회를 실행한다.
7. 출발편 결과 원문을 저장한다.
8. 상품일수 기준으로 귀국편 후보일을 만든다.
9. 귀국편 후보일별 TOPAS 조회 명령을 생성한다.
10. TOPAS에 귀국편 후보 명령을 순차 입력하고 AC1 반복 조회를 실행한다.
11. 귀국편 결과 원문에서 실제 출발시간을 날짜별로 파싱한다.
12. 실제 귀국편 출발시간 기준으로 박수를 자동 계산한다.
13. 날짜별 운항 여부와 가용 클래스를 요약한다.
14. 요금계산을 수행한다.
15. 엑셀 파일을 생성한다.

## 조회 기간 정책

기본 조회 기간:

```text
조회 시작일 ~ 조회 종료일
```

예시:

```text
조회 시작일이 2026-06-29이고 조회 종료일이 2027-06-23이면 두 날짜를 포함한 360개 날짜를 조회한다.
```

구현 기준:

- MVP GUI에서는 조회 시작일과 조회 종료일을 직접 입력한다.
- 기본값은 조회 시작일 오늘, 조회 종료일 오늘 + 359일로 둔다.
- 두 날짜를 모두 포함해 날짜 목록을 만든다.
- 조회 날짜 수는 안전을 위해 1~366일 범위로 제한한다.

파일명 후보:

```text

```

```js
export const flightMasters = [

    rawKey: "ICNDAD_ZE593/4",

    destination: "DAD",
```

귀국편 시간 처리 원칙:

```js

```

기본은 `retDepartureTime: null`이다. 박수는 마스터의 고정값으로 확정하지 않고, TOPAS 귀국편 결과에서 날짜별 실제 출발시간을 파싱해서 확정한다.

`retDepartureTime`은 예외적인 임시 보정값 또는 수동 확인용으로만 사용한다. 같은 항공사/노선/편명도 시즌에 따라 23시대 귀국과 01시대 귀국이 섞일 수 있기 때문이다.

## 박수 계산 설계

입력값:

- 상품일수
- TOPAS 귀국편 결과에서 파싱한 날짜별 현지 출발시간

규칙:

```text
귀국편 출발시간이 00:00 이후 새벽이면 박수 = 상품일수 - 1
귀국편 출발시간이 24:00 이전 밤이면 박수 = 상품일수 - 2
```

MVP에서는 단순하게 아래처럼 처리한다.

```text
00:00 <= 귀국편 출발시간 < 06:00 = 새벽 출발
18:00 <= 귀국편 출발시간 <= 23:59 = 밤 출발
```

중간 시간대가 있으면 수동 확인 대상에 넣는다.

예시:

| 상품일수 | 귀국편 시간 | 계산 박수 |
|---:|---|---:|
| 5일 | 23:30 | 3박 |
| 5일 | 00:30 | 4박 |
| 6일 | 23:30 | 4박 |
| 6일 | 00:30 | 5박 |

## 날짜별 귀국시간 감지 설계

고정 귀국시간 방식은 사용하지 않는다.

이유:

- 같은 항공사, 같은 노선, 같은 귀국편이라도 시즌에 따라 귀국편 시간이 바뀔 수 있다.
- 예를 들어 A시즌은 23시대 리턴이라 3박, B시즌은 01시대 리턴이라 4박이 될 수 있다.
- 따라서 노선/편명 마스터에 귀국시간 하나를 박아두면 시즌 경계 날짜에서 요금계산 기준이 틀어질 수 있다.

감지 방식:

1. 출발일과 상품일수 기준으로 가능한 귀국 후보일을 만든다.
2. 5일 상품이면 `상품일수 - 2박`, `상품일수 - 1박` 두 후보를 만든다.
3. 예: 2026-07-01 출발 5일 상품이면 2026-07-04 귀국 후보와 2026-07-05 귀국 후보를 모두 조회한다.
4. TOPAS 귀국편 결과에서 지정 편명의 실제 출발시간을 파싱한다.
5. 실제 출발시간이 18:00~23:59면 밤 출발로 보고 `상품일수 - 2박`을 확정한다.
6. 실제 출발시간이 00:00~05:59면 새벽 출발로 보고 `상품일수 - 1박`을 확정한다.
7. 두 후보 모두 운항하거나 둘 다 파싱되지 않으면 `시간확인필요`로 남기고 로그에 기록한다.

저장해야 할 감지 결과:

| 필드 | 설명 |
|---|---|
| `baseDepartureDate` | 상품 출발일 |
| `routeKey` | 마스터 키 |
| `candidateReturnDate` | 조회한 귀국 후보일 |
| `detectedReturnTime` | TOPAS에서 파싱한 실제 귀국편 출발시간 |
| `detectedNights` | 확정 박수 |
| `detectionStatus` | 확정, 비운항, 후보충돌, 파싱실패, 수동확인 |
| `rawFile` | 근거 원문 파일 |

## TOPAS 명령 생성 설계

출발편 명령:

```text
AN{DDMMM}{origin}{destination}/A{airline}{depFlightNumber}
```

귀국편 명령:

```text
AN{DDMMM}{destination}{origin}/A{airline}{retFlightNumber}
```

예시:

```text
마스터: ICNDAD_ZE593_594
출발일: 2026-07-01
상품일수: 5일
귀국편 시간: 23:30
박수: 3박
```

생성 결과:

```text
출발편: AN01JULICNDAD/AZE593
귀국편: AN04JULDADICN/AZE594
```

귀국편 시간이 00:30이라 4박이면:

```text
귀국편: AN05JULDADICN/AZE594
```

## TOPAS 실행 설계

기존 ERPUpdater 재사용 후보:

- `topas.availability.build_availability_commands`
- `topas.availability.build_ac1_workflow_commands`
- `topas.availability.parse_availability_text`
- `topas.pacing.TopasPacingPolicy`
- `topas.collector.save_raw_backup`

브라우저:

- TOPAS 디버그 크롬 기본 포트: `127.0.0.1:9222`
- ERP와 분리해서 운용한다.

실행 원칙:

- 노선/편명 단위로 출발편 조회를 먼저 끝낸다.
- 출발편 원문을 저장한다.
- 같은 노선/편명 단위로 귀국편 조회를 실행한다.
- 귀국편 원문을 저장한다.
- 대량 조회 중간에 실패하면 마지막 성공 지점부터 재시작할 수 있게 run log를 남긴다.

## 요금계산 설계

1차 요금계산은 기존 ERPUpdater의 `fare.calculator` 방식을 재사용할 수 있다.

필요 데이터:

- 출발편 TOPAS 원문
- 귀국편 TOPAS 원문
- 노선 코드
- 박수
- 운임/시즌 스냅샷

계산 방식:

1. TOPAS 원문에서 날짜별 가용 클래스를 추출한다.
2. 운임 DB에서 노선/시즌/클래스별 왕복운임을 찾는다.
3. 왕복운임을 편도 기준으로 나눈다.
4. 출발편 편도 + 귀국편 편도를 더한다.
5. 마감 또는 미등록 클래스는 별도 상태로 표시한다.

주의:

- 이 방식은 실시간 TOPAS `FXP/FQQ` 운임조회가 아니다.
- 실제 발권 운임 검증이 필요하면 향후 `FXP/FQQ` 기반 별도 모듈을 추가해야 한다.

## 구현 방식 선택

추천 방식:

- 마스터와 신규 오케스트레이션은 `mjs`로 둔다.
- TOPAS 실행/파싱/요금계산은 기존 Python 코드를 재사용한다.
- Node에서 Python 모듈을 직접 호출하기보다, 중간 JSON/파일을 기준으로 연결하면 안정적이다.

대안:

- 전체를 Python으로 통합할 수 있다.
- 하지만 사용자가 명시한 마스터 형식이 `mjs`이므로, 마스터 데이터는 `mjs`로 시작하는 편이 좋다.

## 리스크와 확인 필요 사항

| 항목 | 리스크 | 대응 |
|---|---|---|
| 귀국편 시간 미확정 | 박수 자동 계산 불가 | 귀국 후보일을 조회하고 TOPAS 응답의 실제 출발시간을 날짜별 파싱 |
