## 2026-06-29 MVP GUI/엑셀 초안

요청:

- 항공자동조회 프로젝트를 기존 ERP 업로드와 분리한다.
- MVP로 GUI와 결과 엑셀 파일을 먼저 만들어 본다.

생성 파일:

- `flight-master.mjs`
  - 사용자가 제공한 19개 노선/항공편 마스터를 `mjs` 데이터로 정리했다.
  - 귀국편 출발시간은 아직 확인 전이므로 `retDepartureTime: null`로 둔다.
- `air_auto_lookup_mvp.py`
  - 초기 Tkinter GUI로 조회 시작일, 조회일수, 상품일수, 귀국시간 미입력 처리 방식을 입력했다.
  - `flight-master.mjs`를 읽어 선택한 노선/편명 기준으로 조회계획 엑셀을 생성한다.
  - 실제 TOPAS 자동입력은 아직 붙이지 않고, 출발/귀국 TOPAS 명령과 조회 전 상태를 엑셀에 만든다.
- `run_mvp.bat`
  - GUI 실행용 배치 파일이다.

검증:

- `python -m py_compile air_auto_lookup_mvp.py` 통과.
- 샘플 생성 명령:

```powershell
python air_auto_lookup_mvp.py --sample --start-date 2026-06-29 --days 360 --product-days 5 --fallback-mode before_midnight
```

- 생성 파일:



## 2026-06-29 시즌별 귀국시간 변동 반영

요청:

- 같은 항공사, 같은 노선, 같은 편명이어도 시즌에 따라 귀국시간이 23시대 또는 01시대로 바뀔 수 있다.
- 시스템이 이 차이를 파싱 또는 감지해서 날짜별 박수를 계산해야 한다.

정리:

- `flight-master.mjs`의 `retDepartureTime` 하나로 전체 기간 박수를 고정하면 안 된다.
- 기본 정책은 TOPAS 귀국편 조회 결과에서 날짜별 실제 귀국편 출발시간을 파싱하는 것이다.
- 5일 상품은 3박 후보일과 4박 후보일을 모두 만들고, 실제 운항/출발시간으로 최종 박수를 확정한다.
- 6일 상품은 4박 후보일과 5박 후보일을 같은 방식으로 처리한다.

코드 반영:

- `return_candidate_dates()`를 추가해 상품일수 기준 가능한 귀국 후보일을 만든다.
- `build_plan_rows()`가 `detected_return_times`를 받을 수 있게 바꿨다.
- 날짜별 감지값이 있으면 그 시간으로 박수를 계산한다.
- 감지값과 마스터 보정값이 모두 없으면 `귀국시간감지필요` 상태와 후보 귀국 명령을 남긴다.
- GUI의 `귀국시간 미입력 처리` 선택 UI를 제거하고 `TOPAS 결과 날짜별 감지` 문구로 바꿨다.
- 편명 목록의 귀국시간 칸은 고정시간이 없으면 `날짜별 감지`로 표시한다.

- live 반복도 `--skip-existing` 없이 실행하면 같은 명령을 다시 선택할 수 있는 구조였다.
- 실패 raw가 있더라도 후처리 단계에서는 일반 `parse_failed`로만 보일 수 있었다.
- 운임 계산 단계에서 `fare_route_missing`을 너무 먼저 판단해, 실제 `raw_missing`/`no_flight` 상태가 최종 `fare-results.json`과 요약 시트에서 가려졌다.
  - 예: `output\logs\20260629_181335`는 출발 결과가 `no_flight 11`, `raw_missing 349`였지만, 수정 전 최종 운임 결과는 `fare_route_missing 360`으로만 표시됐다.

반영:

- `topas_live_collector.py`
  - `--loop-until-done`에서는 `limit`를 배치 크기로 사용하고, dry-run/live 모두 다음 배치로 전진하도록 수정했다.
  - 반복 실행 중 이미 처리한 명령 ID를 메모리에서 제외해 같은 실행 안에서 동일 명령이 반복되지 않게 했다.
  - `--loop-until-done`은 운영 안전을 위해 `--skip-existing` 기준을 함께 적용하도록 했다.
  - dry-run도 `[dry-run batch N] TOPAS 명령 X개` 형태로 배치별 진행을 출력한다.
  - `--max-batches`가 dry-run/live 양쪽에서 반복 제한으로 동작하게 했다.
- `air_auto_lookup_mvp.py`
  - `TOPAS_COLLECT_ERROR` raw를 `collect_failed` 상태로 후처리하도록 추가했다.
  - 귀국 후보가 모두 미수집이면 `return-night-results.json`에서 `raw_missing`으로 남도록 수정했다.
  - 운임 계산의 상태 우선순위를 조정했다.
    - 출발 raw 미수집/수집 실패/NO FLIGHT
    - 귀국 박수 미확정/미수집/수집 실패/NO FLIGHT
    - 그 다음 운임 DB route 존재 여부
  - 최종 `fare-results.json`에서 `departure_raw_missing`, `departure_no_flight`, `return_raw_missing` 같은 운영 상태가 보이도록 했다.
  - GUI 백그라운드 작업 완료 후 현재 run의 상태 집계를 작업 로그에 출력하도록 했다.
  - GUI `전체 수집`/`출발 수집`/`귀국 수집`은 계속 `--skip-existing --live --process-after --calculate-after --loop-until-done` 조합으로 실행한다.

## 2026-06-30 GUI 자동 실행 버튼 추가

요청:

- 사용자가 날짜 설정과 노선 선택 후 플레이 버튼을 누르면 `run.json` 생성, `command-plan.json` 생성, 기본 결과 엑셀 생성, 전체 수집 시작까지 자동으로 이어지는 흐름이 더 낫지 않냐는 의견.

판단:

- 기존 `엑셀 생성` 후 `전체 수집` 2단계는 개발/검증에는 명확하지만, 실제 운영에서는 사용자가 매번 순서를 기억해야 한다.
- 운영 기본 흐름은 `자동 실행` 버튼 하나로 묶는 것이 맞다.
- 단, 기존 `엑셀 생성` 버튼은 수집 없이 계획/엑셀만 만들고 싶을 때 필요하므로 유지한다.

반영:

- GUI 조회 조건 영역에 `자동 실행` 버튼을 추가했다.
- `자동 실행` 동작:
  1. 현재 조회 시작일/종료일/상품일수/노선 선택값 검증
  2. 새 run 생성
  3. `run.json` 생성
  4. `command-plan.json` 생성
  5. 기본 결과 엑셀 생성
  6. 현재 실행 로그를 새 run으로 자동 선택
  7. 필터를 `raw-missing`으로 맞춤
  8. `전체 수집`과 같은 `--direction all --skip-existing --live --process-after --calculate-after --loop-until-done` 명령 실행
- 기존 `generate_excel()` 내부 준비 로직을 `create_run_from_current_inputs()`로 분리해 `엑셀 생성`과 `자동 실행`이 같은 준비 코드를 쓰게 했다.

## 2026-06-30 중간 엑셀 생성 중단 및 세이브 날짜 안전장치

요청/문제:

- 수집 중간에 엑셀이 생기면 최종 결과인지 중간 결과인지 헷갈린다.
- 엑셀은 최종 계산까지 다 끝났을 때만 만들어지면 된다.
- 이어 실행에 필요한 저장 데이터는 엑셀이 아니라 raw/json 세이브다.
- GUI에서 조회 시작일/종료일을 바꾼 뒤 `TOPAS 수집 / 후처리` 섹션의 `전체 수집`을 누르면, 화면 날짜가 아니라 기존 선택 run의 전체 날짜가 조회되는 문제가 있었다.

원인:

- 기존 `전체 수집`은 화면의 조회 시작일/종료일을 읽지 않고, 현재 선택된 `output\logs\{runId}\command-plan.json`을 그대로 실행한다.
- GUI 시작 시 최신 run이 자동 선택되어 있으면, 사용자가 화면 날짜를 바꿔도 선택 run은 바뀌지 않는다.
- 자동 수집의 `--calculate-after`가 각 배치 후 `calculate_run_fares()`를 호출했고, 이 함수가 매번 계산 엑셀까지 저장했다.

반영:

- 자동 수집 중간에는 엑셀을 만들지 않도록 변경했다.
  - `topas_live_collector.py`의 배치 후처리에서는 `fare-results.json`까지만 갱신한다.
  - 모든 raw 파일이 수집 완료된 경우에만 마지막에 최종 계산 엑셀을 생성한다.
  - `calculate_run_fares(..., write_excel=False)` 옵션을 추가해 중간 계산과 최종 엑셀 생성을 분리했다.
- `run.json`의 엑셀 상태를 구분했다.
  - 중간 계산: `excelStatus: pending_final_collection`
  - 최종 엑셀 생성 완료: `excelStatus: final_generated`
  - 중간 계산에서는 오래된 `calculatedExcel` 경로를 제거해 사용자가 중간/과거 엑셀을 최종 결과로 오해하지 않게 했다.
- `자동 실행`은 더 이상 시작 시 기본 결과 엑셀을 만들지 않는다.
  - 새 run 생성
  - `command-plan.json` 생성
  - raw 저장 폴더 준비
  - 전체 수집 시작
  - 최종 엑셀은 전체 raw 수집 완료 후 생성
- `전체 수집` 버튼명을 `이어 실행`으로 바꿨다.
  - 의미: 현재 선택된 세이브/run을 이어서 실행한다.
- 날짜/노선 불일치 안전장치를 추가했다.
  - 화면의 조회 시작일/종료일/상품일수/노선과 선택된 run의 조건이 다르면 `이어 실행`, `출발 수집`, `귀국 수집`이 시작되지 않는다.
  - 새 날짜/노선으로 시작하려면 `자동 실행`을 누르도록 안내한다.
- `로그 선택`으로 세이브를 고르면 해당 run의 날짜/상품일수/노선을 화면에 자동 반영한다.
