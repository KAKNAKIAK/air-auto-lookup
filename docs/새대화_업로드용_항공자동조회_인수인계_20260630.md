## 최종 목표

사용자는 GUI에서 조회시작일/조회종료일/노선을 선택한 뒤 `자동 실행` 또는 이어 실행 흐름을 눌러두고 퇴근하면, 다음날 아침 아래가 완료된 상태를 원한다.

- TOPAS AN 명령을 조회기간 끝까지 자동 실행
- raw 저장
- raw 후처리
- 운임 DB 계산
- 요약 시트 포함 최종 계산 엑셀 생성
- 최종 엑셀에서 성공/실패/미수집/조회오류/비운항 상태를 바로 확인

중요한 운영 원칙:

- `limit`는 총 실행 개수가 아니라 배치 크기다.
- 예: `--limit 10`이면 10개만 하고 끝나는 것이 아니라, 10개씩 반복한다.
- `전체 수집`, `출발 수집`, `귀국 수집`은 각각 남은 명령이 없을 때까지 반복되어야 한다.
- 이미 raw 파일이 있으면 skip-existing 기준으로 건너뛴다.
- timeout/오류 1건 때문에 전체 작업이 멈추면 안 된다.
- 실패 건은 로그와 결과에 남기고 다음 명령으로 계속 진행한다.
- 실패 명령이 무한 반복되면 안 된다.
- 최종 엑셀은 수집/후처리/운임 계산이 끝난 뒤 생성되는 것이 사용자 관점에서 맞다.

## 사용자와 나눈 UX 결정

현재 릴리즈 UX 방향:

- 사용자는 날짜/노선 선택 후 `자동 실행`을 누르는 흐름이 가장 좋다.
- 엑셀을 먼저 누르고 수집하는 방식은 사용성이 좋지 않다.
- `자동 실행`은 새 run 생성부터 TOPAS 전체 수집까지 시작한다.
- 시작 시 기본 결과 엑셀은 만들지 않는다.
- 최종 계산 엑셀은 모든 raw 수집이 끝난 뒤 생성한다.
- `계산 엑셀 열기`는 `run.json`의 `calculatedExcel` 경로를 여는 버튼이다.
- `로그 선택`은 기존 작업 세이브를 선택하는 기능이다.
- 세이브 파일의 실체는 주로 `run.json`, `command-plan.json`, 결과 JSON, raw 폴더다.
- raw 파일은 사용자에게 직접 노출할 필요가 적고, 내부 자료 취급이 맞다.
- 중간에 멈추고 이어서 멈춘 지점부터 다시 도는 기능이 필요하다.

릴리즈 기준 버튼 정리 방향:

- 메인: `자동 실행`
- 이어하기: `로그 선택`, `이어 실행`
- 확인: `계산 엑셀 열기`, `로그 열기`
- 고급/복구: `출발 수집`, `귀국 수집`, `raw 후처리`, `운임 계산`
- `필터` UI는 제거했다. 사용자가 고르는 것이 아니라 프로그램이 세이브/raw 상태를 보고 판단해야 한다.

## 현재 주요 수정 사항

### 1. limit 배치 반복

`topas_live_collector.py --loop-until-done`에서 `--limit`는 총량이 아니라 배치 크기로 동작하도록 고쳤다.

검증했던 예:

```powershell
python -X utf8 topas_live_collector.py output\logs\20260629_181335 --direction return --filter raw-missing --limit 2 --max-batches 2 --loop-until-done
```

결과:

```text
[dry-run batch 1] TOPAS 명령 2개
[dry-run batch 2] TOPAS 명령 2개
totalBatches: 2
totalCommands: 4
```

### 2. GUI 자동 실행 및 세이브 기준 이어하기

`air_auto_lookup_mvp.py` GUI에 `자동 실행` 버튼을 추가했다.

동작:

- 현재 화면 입력값으로 run 생성
- `command-plan.json` 생성
- `전체 수집` 흐름 시작
- 시작 시 엑셀은 만들지 않음

`전체 수집` 버튼명은 `이어 실행`으로 변경했다.

안전장치:

- 선택된 run의 시작일/종료일/상품일수/노선과 현재 화면 입력이 다르면 `이어 실행`, `출발 수집`, `귀국 수집`이 시작되지 않는다.
- 새 조건으로 시작하려면 `자동 실행`을 눌러야 한다.

### 3. 중간 엑셀 생성 중단

수집 중간에는 `fare-results.json`까지만 갱신하고 최종 엑셀은 만들지 않도록 했다.

동작:

- `calculate_run_fares(..., write_excel=False)`:
  - `fare-results.json` 생성
  - `excelStatus: pending_final_collection`
  - `calculatedExcel` 제거
- 모든 raw 수집 완료 후 `write_excel=True`:
  - 최종 xlsx 생성
  - `excelStatus: final_generated`
  - `calculatedExcel` 기록

엑셀이 열려 있어서 저장 실패하는 문제도 보완했다.

- `save_workbook_with_fallback()` 추가
- 대상 xlsx가 열려 있으면 `_재생성_YYYYMMDD_HHMMSS.xlsx`로 저장

### 4. 필터 UI 제거

### 6. 조회 오류를 인디비마감으로 오판하지 않게 수정

문제:

2026-11-09는 실제로는 TOPAS 조회 오류였는데, 노선 시트에서 빈 가격이 `인디비마감`처럼 보일 수 있었다.

raw:

```text
output\raw\20260630_093409\PUSDAD_LJ763_764\departure\2026-11-09_departure.txt
COMMAND: AN09NOVPUSDAD/ALJ763
ERROR: Message: stale element reference: stale element not found in the current frame
```

해석:

- 항공편 마감이 아니다.
- TOPAS 화면 갱신 타이밍에 Selenium이 이전 화면 요소를 읽으려다 실패한 조회 오류다.

수정:

- `collect_failed`는 사용자용 상태 `조회오류`로 표시
- `stale element reference`는 사용자용 문구로 표시:

```text
TOPAS 화면이 갱신되어 조회 결과를 읽는 중 오류가 발생했습니다. 재시도 필요
```

- 노선별 시트에 `상태`, `확인사항` 컬럼 추가
- 요약 시트의 확인 필요 영역에 상태/상세상태/사유 표시
- 최저가 공식에서 `조회오류`를 `인디비마감`보다 우선 표시

검증:

```text
PUSDAD 시트 2026-11-09:
- LJ763 가격 칸: 조회오류
- 상태: 조회오류
- 확인사항: TOPAS 화면이 갱신되어 조회 결과를 읽는 중 오류가 발생했습니다. 재시도 필요

요약 시트:
- 조회오류 1
- 확인 필요 행에 departure_collect_failed 표시
```

### 7. 귀국 후보 TOPAS 중복 조회 방지

문제:

귀국 후보는 3박/4박 후보가 겹친다.

예:

```text
AN05JULDADICN/ALJ082
- 2026-07-01 출발의 4박 귀국 후보
- 2026-07-02 출발의 3박 귀국 후보
```

기존에는 raw 경로가 `출발일 + 박수` 기준이라 같은 TOPAS 명령도 서로 다른 파일로 저장되었다.

수정:

- 새 command-plan부터 귀국 raw는 `귀국 조회일` 기준 저장

기존:

```text
{baseDepartureDate}_return_{nights}n.txt
```

변경:

```text
{candidateReturnDate}_return.txt
```

- 수집기에서 같은 TOPAS 명령은 한 번만 실행
- 필요한 raw 파일이 여러 개면 같은 결과를 여러 대상에 저장
- dry-run 출력에 `(raw 2개)` 표시

검증:

```text
ICN-DAD 2026-07-01~2026-07-03
return logical rows: 24
unique return raw: 16
unique command: 16
```

기존 `20260630_101630` run은 이미 예전 command-plan으로 생성되어 예전 파일명이 보일 수 있다. 하지만 수집기는 같은 TOPAS 명령을 한 번만 실행하도록 보정되어 있다.

특히 주의:

- `NO FLIGHT`는 마감이 아니라 `비운항`
- `stale element reference`는 마감이 아니라 `조회오류`
- raw가 있더라도 `TOPAS_COLLECT_ERROR` 파일이면 재시도 대상이어야 한다.

## 남은 이슈 / 다음 작업 후보

### 1. 조회오류 재시도 정책

아직 명확히 완성되지 않은 부분.

현재 `raw-missing` 기준은 raw 파일이 있으면 건너뛴다. 그런데 실패 raw도 파일로 존재한다.

필요한 정책:

- `TOPAS_COLLECT_ERROR` raw는 `조회오류`로 표시
- 사용자가 `조회오류 재시도` 또는 `이어 실행`을 누르면 실패 raw만 다시 수집할 수 있어야 함
- 실패 raw 재시도 후 성공하면 기존 error raw를 정상 raw로 덮어도 됨
- 단, 무한 반복 방지를 위해 재시도 횟수/마지막 실패 사유를 기록하는 것이 좋음

### 2. 진행 표시 개선

사용자가 “또 두 번 돈다”고 느낄 수 있다.

원인:

- logical 후보 row와 실제 TOPAS unique command 수가 다르다.
- 비운항 확인용 날짜 조회도 정상적으로 필요하다.

GUI에 아래를 분리 표시하면 좋다.

```text
논리 후보: 1476
실제 TOPAS 조회 대상: 988
완료: 564
미수집: ...
비운항: ...
조회오류: ...
```

### 3. 중지/이어하기 버튼

사용자는 중간에 멈추고 멈춘 지점부터 이어가는 버튼이 필요하다고 말했다.

현재 이어하기는 raw-existing/raw-missing 기반으로 동작하지만, GUI에 명확한 `중지` 버튼 또는 실행 중 프로세스 제어 UX는 아직 더 다듬어야 한다.

### 4. 실제 TOPAS live 소량 재검증

수정 후 아래 조건으로 다시 확인 필요:

```powershell
python -m py_compile air_auto_lookup_mvp.py topas_live_collector.py
python -X utf8 topas_live_collector.py <log_dir> --direction all --filter raw-missing --limit 1 --max-batches 2 --loop-until-done --live --process-after --calculate-after
python -X utf8 topas_live_collector.py <log_dir> --direction all --filter raw-missing --limit 5 --max-batches 2 --loop-until-done --live --process-after --calculate-after
```

단, 실제 대량 live는 소량 검증 후 진행.

### 5. 기존 실행 중 GUI/collector 재시작

이미 실행 중인 Python GUI/collector는 수정 전 코드를 물고 있을 수 있다.

새 수정 확인 전에는 GUI를 재시작하는 것이 안전하다.

## 마지막 검증 명령

가장 최근 확인:

```powershell
python -m py_compile air_auto_lookup_mvp.py topas_live_collector.py
```

통과.

## 새 대화 첫 지시 예시

새 대화에 아래처럼 시작하면 된다.

```text
이 파일과 작업일지.md를 읽고 항공자동조회 프로젝트를 이어서 진행해줘.
현재 핵심은:
1. 조회오류 재시도 정책/버튼

3. 비운항/조회오류/마감 상태가 엑셀과 GUI에서 정확히 구분되는지 검증
```
